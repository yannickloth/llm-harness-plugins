# graphrag — Assumptions

This file lists what the graphrag plugin assumes about its runtime: the opencode plugin API, the host environment, filesystem layout, external services, configuration, concurrency, and data/LLM behavior. Assumptions marked ⚠ are fragile: a change on the other side (opencode release, host machine, graphrag release, consumer project layout) breaks the plugin without a test failing.

## OpenCode API

- ⚠ The plugin ships two entrypoints in one module (`opencode/index.ts`): a v1 function export `server(input, options)` (line 787) and a v2 default export `{ id, setup }` (line 494). Which one runs depends on the host opencode version; they are near-duplicate code that must be kept in parity by hand.
- ⚠ opencode 2.x (verified on 2.2.5, the installed host) consumes only the default-export module schema `{ id, setup | effect }`. The `server` property on the same object is ignored, so the ~300-line v1 path is dead code on this host. It is live on opencode 1.x hosts (1.19.3 calls `server(input, options)`).
- ⚠ v1 and v2 use different event names for the same watcher facts. v1 (1.19.3) emits `file.edited` and `file.watcher.updated`; v2 (2.2.5) emits only `filesystem.changed` with `data.event ∈ {add, change, unlink}`. The v2 handler (index.ts:610–617) still listens for the v1 names, so watcher-driven dirty tracking is dead on 2.2.5 (see report BUG).
- ⚠ v1 `tool.execute.after` hook payload is `{ tool, sessionID, callID, args }` (verified in 1.19.3 `prompt.ts` and in `@opencode-ai/plugin` 1.18.18 typings). There is no `input` field; the v1 handler reads `event.input` and throws (see report BUG). The v2 `ctx.tool.hook("execute.after")` payload does carry `input` (plus `sessionID`, `agent`, `messageID`, `id`, `status`, `result`), and the v2 handler reads `event?.input ?? event?.args` correctly.
- ⚠ `session.idle` is used as the auto-update trigger on both paths. In 2.2.5 it is a deprecated-but-present member of the subscribable event union (`data: { sessionID }`); multiple sibling plugins in this repo depend on it in v2 mode. If a future opencode drops it, auto-update dies silently (no other event triggers it).
- ⚠ `session.created` payload shape differs across versions: v1 carries `properties.info.id`, v2 carries `data.sessionID`. The v2 handler (index.ts:592) reads both; the v1 handler reads only `properties.info.id`.
- The v1 loader (opencode 1.x) treats every top-level function export of the entry module as a plugin factory; shared helpers therefore live in `lifecycle.ts` and `spawn-slot.ts` and are never re-exported from `index.ts` (module header comments, spawn-slot.ts:8–13).
- `ctx.tool.hook` and `ctx.event.subscribe` (v2) and the returned `{ event, "tool.execute.after", tool }` object (v1) are assumed to be fire-and-forget: hook errors in the event loop are caught by a blanket `try/catch` around the subscription loop (index.ts:658–660) and swallowed ("the event stream is best-effort").
- ⚠ Tool name set for dirty tracking is exactly `{ read, glob, grep }` (index.ts:33). If opencode renames a tool or adds a new file-reading tool, dirty tracking misses it.
- Status injection uses version-specific APIs: v1 `client.session.prompt({ noReply: true })`, v2 `ctx.session.synthetic`. Both are assumed to accept synthetic/system-style messages without a model reply.
- ⚠ v1 resolves the project root as `worktree ?? directory`; v2 as `location.project.canonical ?? location.directory` (index.ts:186, 501). In a git worktree these can anchor the index to different directories; this is a repo-wide pattern, not a graphrag-specific choice.

## Environment

- ⚠ The plugin is POSIX-only: binary resolution is `command -v` via bun `$` (index.ts:101–105), liveness checks are `kill -0` (spawn-slot.ts:19,45) or `ProcessHandle.of` (IndexCli.java:831), and `Bun.spawn`/`Bun.spawnSync` are used directly. Windows is not supported.
- ⚠ PID liveness by `kill -0`/`ProcessHandle` is subject to PID reuse: a dead lock owner whose PID was recycled reads as "alive", permanently blocking the spawn slot / index lock on this host until the reused process exits.
- `java` ≥ 25 on PATH (code is compiled `--release 25` by the repo-root `build.sh`); `bun` on PATH (the plugin entry itself runs under bun inside opencode); `python3` on PATH (version probe only); `pandoc` on PATH (LaTeX→Markdown, called by Java with the literal binary name `pandoc`); `direnv` on PATH (env fallback, optional — its absence is tolerated).
- ⚠ The `graphrag` CLI (Python package) must be on PATH; the flake dev shell supplies a pinned graphrag 2.7.0 (via `nixpkgs-graphrag` input rev `8ce4ef6c…`), not an arbitrary version. The version check (index.ts:107–117) probes `importlib.metadata.version('graphrag')` — the package name is hardcoded, not derived from the configured `graphrag_binary` (see report).
- The Java indexer assumes a JVM default charset in which UTF-8 is the encoding for `Files.readString`/`writeString` of `.typ`/`.tex`/`.md` content; a non-UTF-8 `file.encoding` corrupts exported text.
- The dev shell (`flake.nix`) provides only graphrag (python312 override with the `np.float_`→`np.float64` patch) and pandoc; `java`, `python3`, `direnv`, `bun` must come from outside the shell.
- Environment variables: `DEEPSEEK_API_KEY` (chat), `GRAPHRAG_API_KEY` (embedding; any non-empty value works because the endpoint is local LM Studio). Resolution chain per key (lifecycle.ts:105–116): `process.env` → `<indexRoot>/.env` → `<root>/.env` → `direnv exec <root> printenv <name>` with a 20 s cap.
- ⚠ `resolveBinary`/`resolveEnvKey` assume the opencode process's own `PATH` and environment see the same tools/keys as the user's shell; starting opencode outside the project's direnv shell is a documented failure mode ("start opencode from the project terminal so direnv loads", index.ts:442).

## Filesystem & layout

- Index root is `<project>/graph-index/` (config `index_root: graph-index`), containing: `input/` (exported content-addressed Markdown), `output/` (promoted graphrag artifacts: parquets + lancedb), `update_output/<timestamp>/` (graphrag staging for `update`), `prompts/` (copied from the plugin dir), `settings.yaml`, `cache/`, `logs/` (run logs + graphrag reporting base_dir), `manifest.json`, `.lock`, `.spawn-lock`, `.last-launch`.
- ⚠ `lancedb/` lives directly under `graph-index/` (settings.yaml `db_uri: lancedb`, relative to the graphrag CWD, which is the index root). The mode gate checks `graph-index/lancedb` non-empty (lifecycle.ts:143–148); a graphrag release that relocates the DB breaks the gate.
- graphrag runs with CWD = index root, because `settings.yaml` uses relative `base_dir`s (`input`, `output`, `update_output`, `cache`, `logs`, `lancedb`). Any change of the spawn CWD (Bun.spawn inherits the opencode CWD, not the index root — the `--root`/`--config` flags carry the paths instead) depends on graphrag resolving them correctly.
- Content-addressed export files are named `<docId>--<sha8>.md` (DocumentWriter.java:91–93); `docId` is derived from (source doc, kind, block identity). Dirty-file deletion matches the md frontmatter `file:` line via regex `^file:\s*(.+)$` (IndexCli.java:584) — the exporter and the deleter must keep emitting that exact line (see Data & LLM behavior).
- Atomic manifest writes are tmp+rename on both sides: TS `mergeManifestV2Atomic` (lifecycle.ts:72–74) and Java `writeManifestFile` (IndexCli.java:629–631). ⚠ Both use the same fixed tmp name `manifest.json.tmp` (see report: concurrent writers can corrupt the manifest).
- `input/` is append-only by design: full reindex never deletes stale content-addressed files; only the incremental path removes docs for dirty sources (`removeDocsForSources`, IndexCli.java:572–595). `DocumentWriter.removeStale` exists but is dead code in production.
- The TS dirty-set walk excludes path segments in `EXCLUDE_SEGMENTS` (index.ts:28–31): result, .git, graph-index, tmp, target, build, .direnv, node_modules, downloads, literature. Java uses a different default list (ExportConfig.java:144–145) that additionally contains `.direnv-cache`; the shipped `config/graphrag.yaml` `exclude:` list replaces (does not merge with) the Java default and omits `node_modules` and `.direnv-cache`.
- Relative-path containment checks use string `startsWith(root)` without a path-separator boundary (index.ts:366, 670), so sibling directories sharing a prefix (e.g. `/proj2` under root `/proj`) pass the guard (see report).
- `.last-launch` (debounce timestamp) is written non-atomically (spawn-slot.ts:58); a torn read yields NaN and silently disables the debounce.

## External services

- ⚠ Embedding endpoint `http://localhost:1234/v1` (LM Studio on this host) is probed at `<base>/models` with a 2000 ms timeout before every index spawn (preflight) and before every `local` query (lifecycle.ts:118–126). Any OpenAI-compatible `/models` endpoint works; the model name `text-embedding-nomic-embed-text-v1.5` must exist there.
- ⚠ Chat endpoint `https://api.deepseek.com/v1`, model `deepseek/deepseek-flash` (config). `writeSettings` rewrites the provider: `deepseek/…` model → `model_provider: openai` + `api_base: https://api.deepseek.com/v1` (IndexCli.java:680–696). A non-deepseek provider without `chat_api_base` in the yaml NPEs (see report).
- ⚠ graphrag 2.7.0 validates ALL configured models at process start (index and query). A dead embedding endpoint or missing key aborts the whole run before any workflow; the plugin preflight exists to fail before spawn, not to recover mid-run.
- graphrag has no `--version` flag. Version detection on both sides (TS index.ts:107–117, Java IndexCli.java:649–664) runs `python3 -c "from importlib.metadata import version; print(version('graphrag'))"` — the package name is hardcoded on both sides, not derived from the configured `graphrag_binary` — with a fallback that regex-matches `graphrag-x.y.z` in the resolved binary path (a `.venv/bin/graphrag` yields no version on either side, so the version check is silently skipped).
- Java's PATH resolution (IndexCli.java:666–674) splits `PATH` on `:` and takes the first executable match — POSIX-only, and it may resolve a different `graphrag` than the TS side's `command -v` if the two processes see different PATHs.
- The 20 s `direnv exec` cap means a slow nix dev shell evaluation can cost up to 20 s per missing key per preflight; the "absent everywhere" unit test exercises this real fallback (index.test.ts:212–215).
- Chat requests are subject to the consumer's hand-edited limits (see Configuration); the plugin itself enforces no request timeout beyond graphrag's own `request_timeout` (0 = graphrag default).

## Configuration

- ⚠ The plugin is registered in `opencode.json.sample` (`./graphrag/opencode`, line 15) but NOT in the active repo `opencode.json`; the live consumer (`/home/nicky/code/ivp-book-series`) loads it from its own opencode config. Behavior in the harness repo is therefore off unless the user opts in.
- The single config file is `graphrag/config/graphrag.yaml` (plugin dir), read by two independent parsers with divergent semantics: TS (index.ts:65–99, lenient, substring-based) and Java (ExportConfig.java:61–160, strict `Integer.parseInt`, section tracking). A value one parser accepts the other may crash on (see report: `chat_concurrent_requests: 10x` etc.).
- ⚠ The shipped yaml's `chat_concurrent_requests: 10` contradicts its own comment (lines 5–8) which says a single-slot local server needs 1 (spec E15/FS-9); the local LM Studio server here is single-slot, so the shipped value serializes chat work behind its queue.
- `projects:` entries: `name`, `root`, `latex_root`, `exclude`. ⚠ The Java parser only reads `root:`/`latex_root:`/`exclude:` correctly; `- name:` is a list item and is silently ignored (key arrives as `- name`), so `name` always falls back to the basename of `root`. Multiple project entries overwrite each other (single-project config).
- The Java parser ignores comments only when a line starts with `#` after strip; an inline comment (`key: value # note`) is part of the value for string keys and a parse crash for integer keys.
- `reindex_threshold` (default 400) is parsed in TS but unused there; only Java (which re-reads the yaml) acts on it (full rebuild when dirty > threshold, IndexCli.java:230).
- ⚠ Spec FS-10 (throughput guard: probe output rate, refuse when projected time > `max_index_minutes`, default 120) is unimplemented in both TS and Java; the config key does not exist anywhere.
- `writeSettings` (IndexCli.java:676–807) regenerates `<indexRoot>/settings.yaml` on every `init` and first-run `update`, overwriting any hand edits. The live consumer's `settings.yaml` was hand-edited (extra `report_model`, `CHEAPERINFERENCE_API_KEY`, `max_tokens: 8192`, `concurrent_requests: 4`); any run that hits the (re)write path destroys those tweaks.
- `init-sample <project-root> <config-yaml> <sample-root> [plugin-dir]` has no argument-count check and throws `ArrayIndexOutOfBoundsException` with fewer than 4 args (IndexCli.java:124–127).

## Concurrency

- Three coordination files in `<indexRoot>`: `.lock` (Java, one indexer job at a time; CREATE_NEW + PID + timestamp; steal rules: dead owner → steal, live owner → never steal, unparseable PID → steal unless the lock is < STALE_LOCK_SECONDS old), `.spawn-lock` (TS, cross-session spawn claim; `openSync "wx"` + PID; owner liveness via `kill -0`), `.last-launch` (TS, global debounce timestamp, default 300 s).
- ⚠ The manifest is read-modify-written by two different processes without a shared lock: the TS plugin (dirty adds on every read/glob/grep/file event, status patches on preflight) and the Java indexer (building/complete transitions under `.lock`). A TS merge landing between Java's read and write clobbers the Java state (lost update: `complete` reverted to `building`, or dirty entries dropped). `.lock` protects only Java↔Java.
- Auto-update fires on `session.idle` only when: `auto_update: true`, dirty set non-empty, graphrag binary resolvable, preflight green, and the spawn slot is claimable (no live indexer, not within debounce). A failed preflight sets `status: failed_preflight` and burns the idle tick without claiming the slot.
- The `index` tool mode shares the same spawn-slot throttle as auto-update (index.ts:422, 730); a user-requested `mode=index` can be refused by the debounce even though the user explicitly asked.
- ⚠ `promote()` deletes the live `output/` before moving `update_output/<ts>` into place (IndexCli.java:554–570); a crash in that window loses the entire index.
- `launchDetached` (index.ts:168–177) spawns the Java indexer with stdout+stderr appended to `logs/<init|update>-<epoch>.log`; the parent keeps the `openSync` fd open after spawn (leaked fd per launch in the long-lived opencode process; see report).
- The v1 path registers event + tool hooks for every opencode process that loads the plugin; with multiple concurrent opencode instances on the same project, all of them race on the same manifest and spawn slot (by design, via the shared files).

## Data & LLM behavior

- ⚠ Exported `.md` blocks carry YAML-ish frontmatter written by `DocumentWriter.render`; the incremental deleter relies on the `file:` frontmatter line matching the dirty-set entry exactly (path form: relative to project root, or bare filename — IndexCli.java:574–578 matches both). A format change in the exporter or a path-normalization mismatch silently stops old blocks from being deleted.
- ⚠ `extract_graph.txt` domain-adaptation section (lines 123–132) instructs uppercase entity types derived from label prefixes (`thm=THEOREM … proof=PROOF`) and canonical relationship verbs, but `settings.yaml` `entity_types` (IndexCli.java:782) is lowercase and disjoint (`theorem, definition, lemma, axiom, principle, concept, notation, paper, author, pattern, verdict` — no `proof`). The LLM must improvise the mapping; graphrag may drop or mis-type entities whose type string is not in the configured list.
- Prompt placeholders `{entity_types}`, `{tuple_delimiter}`, `{record_delimiter}`, `${completion_delimiter}` etc. are filled by graphrag (string.Template — hence the intentional `$$` escaping in `file_pattern: ".*\\.md$$"`, design §10.4). The plugin never substitutes into prompts itself.
- `model_supports_json: true` is written unconditionally for the chat model (IndexCli.java:708); it is assumed true for deepseek-flash. `reasoning_effort: low` is written only when non-blank (config default `low`); the assumption is that the chat model honors a reasoning-effort knob and that batch extraction must not spend `max_tokens` on thinking (comment at IndexCli.java:710–711).
- Community reports, claims, and covariates are assumed to be produced by graphrag's workflows with the plugin's prompts (`community_report_graph.txt`, `community_report_text.txt`, `extract_claims.txt`); the mode gates (lifecycle.ts:128–133) assume the artifact filenames `text_units.parquet`, `communities.parquet`, `community_reports.parquet`, `covariates.parquet`, `entities.parquet`, `relationships.parquet` under `output/`. A graphrag release that renames outputs breaks the gates and the query refusal, not the index itself.
- ⚠ graphrag `update` (2.7.0) stages into `update_output/<timestamp>/` and detects changed documents by TITLE (= source filename) only; the plugin compensates with content-addressed md filenames so that same-title content changes produce new input files. If graphrag changes its delta detection, the content-addressing scheme may double-index.
- `TypstBlockSplitter.ENV_MAP` (TypstBlockSplitter.java:12–41) recognizes a fixed set of block environments (theorem, proof, example-env, …); any `#<other-env>[…]` (e.g. `proof-env`, which has no mapping while every sibling does) is silently dropped into prose.
- LaTeX chunks are converted by pandoc per chunk (`-f latex -t markdown --wrap=none`); a pandoc failure silently returns the raw LaTeX as the "markdown" (LatexExporter.java:139, 141–143), so the index can contain raw LaTeX with no error in any log.
- Deduplication: a LaTeX chunk whose label appears in the Typst label set is skipped (`dedup-skipped`, ExportCli.java:106–109), on the assumption that the `.typ` source is authoritative for shared labels. A corpus where `.tex` is authoritative double-counts nothing but loses the `.tex`-only content.
- The manifest `status` vocabulary is `idle | building | complete | partial | failed_preflight | failed_run | stale | unknown` (lifecycle.ts:17); TS and Java must keep writing/reading the same strings. TS's `readManifestV2` defaults a schema-1 manifest (no `schema` field) to `schema: 1` and fills missing fields with defaults.
- `stalenessLine` version-mismatch refusal compares the manifest's `graphrag_version` to the live binary's version; the assumption is that a version change always changes the index format (true for graphrag majors; for patches it can produce needless rebuild refusals).
